# 完整整理（引言＋大標題＋子標題）與匯出改版 設計

> 2026-10-27 使用者決定：不使用 Claude API，完整整理改走 Max 訂閱；本文中 API 相關段落已作廢

日期：2026-10-27。分支：`claude/meetings-edit-0d1c76`。提出者：使用者（不寫程式，靠回報做決策）。

## 為什麼要做

使用者拿一份人工寫好的會議紀錄當範本（`20260116_元澄、兆輝交流會議紀錄.docx`），說現在匯出的 Word 「格式不夠明確」。
現在的匯出是「待辦／會議重點／Q&A」三個區塊平鋪，重點只有一層編號清單。範本是：

- 最前面一段**引言**，說明這份紀錄在講什麼。
- 然後是**大標題**，每個大標題下有**子標題**，子標題的內容是一段完整說明。
- 子標題以「**粗體小標：** 說明」開頭，重要數字可再粗體。
- 最後是待辦（Action Items）與 Q&A。

使用者要的是「錄音內容做更充分的整理」，不只是換排版。AI 整理本身要改，匯出才排得出來。

## 目標

1. 新增一種整理結果「完整整理」：引言 ＋ 大標題 ＋ 子標題。
2. 大標題、子標題的數量和名稱由錄音內容決定，不固定。
3. Word／PDF 匯出照新結構排版：引言 → 大標題與子標題 → 待辦 → Q&A。
4. 完整整理這一步走 Claude API（固定 Opus），API 失敗時自動退回 Max 訂閱重跑。
5. 每一條內容仍然有逐字稿依據（可點回原句），沿用現有「有依據才能寫」規則。

## 非目標

- 不改轉錄（電腦顯卡 Whisper）。Claude API 不能轉錄音檔。
- 不把其他 AI 功能（訂正人名、問答、翻譯、學習筆記）改走 API，這些維持走 Max。
- 不固定要有「公司背景」「團隊」「財務」這類大標題。錄音有提到才出現（使用者決定）。
- 不替使用者補錄音沒講的外部資料（公司簡介、股價、財報）。範本裡那類內容若錄音沒講就不寫。
- 不自動改舊會議。舊會議要按鈕才會有完整整理。
- 不 merge 回 main、不 push、不部署 NAS，除非使用者在對話裡明確要求。

## 反目標（做出來也算失敗）

- 內容聽起來很完整，但有句子在逐字稿找不到依據（編造）。
- 大標題變成固定罐頭（每場都是「背景／產品／財務」），跟錄音不符。
- API 壞掉時，整個整理卡住或報錯，使用者什麼都拿不到。
- API 金鑰出現在 git、log、畫面或對話中。

## 資料結構

在會議的 `summary` 底下新增 `report`（不動既有的 `actionItems`／`mainPoints`／`qa`）：

```json
"report": {
  "intro": {"text": "…", "src": [{"t": 83, "quote": "…"}]},
  "sections": [
    {"heading": "會議討論內容", "subs": [
      {"title": "生意與訂單", "text": "…", "src": [{"t": 410, "quote": "…"}]}
    ]}
  ],
  "via": "api" | "max",
  "model": "claude-opus-5-5",
  "at": 1790000000000
}
```

- `intro`、每個 `sub` 都是現有的「條目」（`text` ＋ `src`），所以沿用現有的依據驗證（`_reverify`）與點回原句功能。
- `heading` 是大標題純文字。大標題本身不需要 `src`，但底下每個子標題要有。
- `via` 記錄這次是 API 還是 Max 產生的，畫面上顯示一個小標籤，方便使用者核對費用。
- 舊會議沒有 `report`：匯出與畫面完全走舊格式，不壞。
- `actionItems` 與 `qa` 沿用現有摘要的產物。若會議還沒有摘要，完整整理一併產生（沿用 `_summary` 的流程）。

### 實作調整（寫計畫時發現，2026-10-27；使用者端看不到差別）

上面的巢狀 `summary.report` 改為**兩個平的條目清單**，因為現有的依據驗證、人名替換、編輯、點回原句都只認「條目清單」，平的結構可以全部沿用，不必改這些功能：

- `summary.reportIntro`：1 個條目（引言）。
- `summary.reportPoints`：多個條目，`group` = 大標題，`text` = 「子標題：說明」（跟現有 `mainPoints` 同格式）。大標題順序 = `group` 第一次出現的順序，由 AI 輸出順序決定，不依時間重排。
- `reportMeta`（會議最上層）：`{via, model, at, stale?, fp}`；`fp` 是產生當下逐字稿的指紋。
- 「有完整整理」的判斷：`reportPoints` 至少有 1 條。

## AI 提示詞（`server/prompts.py`）

新增 `REPORT_PROMPT`、`REPORT_SCHEMA`。重點：

- 第一部分寫引言：2–4 句，說明誰參與、談什麼、有哪幾個主要方向。引言每個事實也要有 `src`。
- 第二部分切大標題：依錄音實際主題切，通常 2–6 個；每個大標題 2–6 個子標題。不套固定範本。
- 子標題：`title` 是 4–14 字名詞短語，`text` 是說明，保留數字、日期、條件、但書、誰說的。範本中的粗體關鍵數字在匯出時由程式處理（見下），提示詞不要求 AI 打粗體標記。
- 完整沿用 `GROUNDING_RULES`（不補全名、不換算、不推測、口誤照實標示）。
- 待辦與 Q&A 不在這一個呼叫裡寫，沿用現有摘要。避免同一件事在兩處重複。
- 逐字稿過長時沿用 `chunk_lines` 分段：每段各產生大標題草稿，再用第二次呼叫合併相同主題、重排順序（沿用 `_grounded_summary` 的分段模式）。

## API 呼叫（新檔 `server/anthropic_api.py`）

- 用官方 `anthropic` 套件，模型固定 `claude-opus-5-5`（簡稱與型號的取捨留給實作者，但不可寫死在多處）。
- 金鑰來源：環境變數 `ANTHROPIC_API_KEY`，由 `compose.yaml` 掛一個唯讀檔案 `/run/meetings/anthropic.key`（與現有 `worker.key` 同做法）。使用者自己把金鑰放到 NAS，不貼對話。
- 金鑰檔不存在或為空 → 視為「API 未啟用」，直接走 Max，不報錯。
- 退回 Max 的條件：沒有金鑰、HTTP 4xx／5xx、額度用完、逾時、回傳不是合法 JSON 或不符 schema。退回時走現有 `run_claude`。
- 兩條路徑都失敗才回報整理失敗，錯誤訊息要同時說 API 與 Max 各是什麼原因。
- 現有 `child_env()` 會刻意濾掉 `ANTHROPIC*` 環境變數，避免 Max 的 `claude` 指令誤用 API 計費。這個行為保持不變：API 金鑰只給 `anthropic_api.py` 用。
- 不在 log 或錯誤訊息中輸出金鑰。

## 伺服器動作

## 匯出（`js/docx.js`、`js/export.js`、`server/render.py`）

有 `report` 時，三處匯出（Word、PDF／HTML、伺服器版 Markdown／docx）都改為這個順序：

1. 標題與日期（沿用）。
2. 引言一段。
3. 每個大標題：編號粗體（「1. 大標題」）；底下每個子標題一個圓點段落，開頭 **粗體小標：**，後接說明。
4. 「Action Items」：i. ii. iii. 清單，結尾保留 `(DRI：…)`。
5. 「Q&A」：沿用現有的 Q／A 兩行格式，編號改為 i. ii. iii.。
6. 逐字稿（若使用者在匯出選項勾選，沿用現有選項）。

- 有 `report` 時，原本「會議重點」區塊不輸出（內容已併入大標題）。
- 粗體關鍵數字：範本有把金額、產能這類數字加粗。第一版不做自動加粗（無法可靠判斷），留給使用者要求後再加。這是我的決定。
- 匯出選項（要不要待辦、Q&A、逐字稿）沿用現有勾選。
- 檔名規則不變。

## 完成標準（使用者看得到、可檢查）

1. **畫面**：打開一場已完成的會議，按「完整整理」，約幾分鐘內詳情頁出現：引言、數個大標題、每個大標題下有子標題；子標題是粗體小標加冒號。
2. **Word 匯出**：用 Word 打開匯出檔，順序是引言 → 編號大標題與子標題 → Action Items → Q&A；沒有獨立的「會議重點」區塊，版面與使用者範本的層次相同。
3. **內容跟錄音走**：用兩場主題不同的會議各按一次，大標題與子標題名稱不同；錄音沒提到公司背景的那場，不會出現公司背景大標題。
4. **有依據**：隨機抽 5 條子標題，每條都能點到逐字稿原句；沒有依據的條目會被標出。
5. **API 與退回**：
   - 放入金鑰：完整整理成功，畫面顯示「由 API 產生」，Anthropic 後台用量有增加。
   - 移除金鑰（或金鑰填錯）：完整整理照樣成功，畫面顯示「由 Max 產生」，不出現錯誤。
6. **舊會議不壞**：沒按完整整理的舊會議，畫面與匯出跟改版前完全一樣。

## 與既有功能的關係（審查後補充，標「我的決定」的是未經使用者逐項確認的判斷）

- **人名訂正（我的決定）**：確認人名訂正時，`report` 的引言與子標題文字一併替換，跟現有摘要條目同一套機制。否則匯出會留著錯名。
- **編輯模式（我的決定）**：引言與子標題可像現有條目一樣編輯、刪除。
- **重新轉錄（我的決定）**：逐字稿重做後，`report` 的 `src` 可能對不上，標記為「已過期」並提示重按完整整理；不自動重跑。
- **重新整理（我的決定）**：整份重做，包含 `report`。
- **API 與 Max 不混用（我的決定）**：同一次完整整理只走一條路。API 任何一段失敗，整次改用 Max 重跑，`via` 只會是單一值。
- **分段合併（我的決定）**：第二次合併呼叫只能重排與合併分組，不可改寫子標題文字；合併後保留原有的全部 `src`。
- **沒有摘要時（我的決定）**：完整整理只產生 `report`。待辦與 Q&A 沿用現有的，沒有就沿用「摘要」流程補，走 Max，不走 API（維持「只有完整整理走 API」）。
- **AI 在哪裡跑**：`server/ai.py` 在 NAS 的會議容器內執行；電腦上的 worker 只負責轉錄。所以金鑰、`anthropic` 套件、網路出口都只放 NAS 會議容器。

## 風險與代價

- 每場多一次 Opus API 費用，會議越長越貴；長會議分段後費用乘以段數。
- 引言與子標題比現有重點更長，更容易出現「看起來合理但沒依據」的句子；靠現有依據驗證擋。
- 要改三處匯出（Word 前端、PDF／HTML 前端、伺服器 docx），需一起測。
